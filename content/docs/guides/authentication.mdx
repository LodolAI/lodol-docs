## Authentication

Every Developer API request is authenticated with an API key, sent as a bearer token in the `Authorization` header.

```bash
curl https://api-prod.lodol.com/api/v1/workflows \
  -H "Authorization: Bearer sk_live_..."
```

The Python SDK sends this header for you. It reads `LODOL_API_KEY` from the environment, or you can pass the key directly:

```python
from lodol import Lodol

client = Lodol()                       # reads LODOL_API_KEY
client = Lodol(api_key="sk_live_...")  # or pass it in
```

### Create and manage keys

Keys are created and revoked in the dashboard under **Settings > API Keys**. Creating or revoking a key requires the manage-API-keys permission, which workspace owners and admins have by default.

A key belongs to one workspace. Every request made with it reads and writes that workspace's data and bills to that workspace. The full key is shown once at creation; Lodol stores only a prefix and a SHA-256 hash, so a lost key cannot be recovered and has to be replaced.

You can set an optional expiration when you create a key by passing `expires_in_days`. After that many days, the key stops working.

### Key format

Keys look like `sk_live_` followed by a random string with 256 bits of entropy. The `sk_live_` prefix is how the API recognizes a Developer API key, so send the whole value, prefix included.

### Scopes

Each key carries one or more scopes. A request to an endpoint the key is not scoped for returns `403`.

| Scope | Grants |
| --- | --- |
| `workflows:read` | List and read workflows |
| `workflows:execute` | Run workflows and stop executions |
| `executions:read` | List and read executions |

Scopes are additive. A key with `workflows:read` and `workflows:execute` can list and run workflows, but it cannot read execution history until you add `executions:read`.

### Plan limits

How many keys a workspace can hold depends on its plan.

| Plan | API keys |
| --- | --- |
| Free | 1 |
| Builder | 3 |
| Pro | 10 |
| Business | 20 |

### Rate limits

Requests are rate limited per workspace, per minute, and the limit is shared across every key in the workspace, so adding keys does not raise the ceiling. There is also a cap on how many executions can run at once.

| Plan | Requests / minute | Concurrent executions |
| --- | --- | --- |
| Free | 3 | 2 |
| Builder | 15 | 4 |
| Pro | 25 | 10 |
| Business | 50 | Custom |

Every response reports your standing in three headers:

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | Requests allowed per minute on your plan |
| `X-RateLimit-Remaining` | Requests left in the current window |
| `X-RateLimit-Reset` | Seconds until the window resets |

Cross the request limit and the API returns `429` with a `Retry-After` header. Start more executions than your plan allows at once and the run endpoint returns `429` naming your concurrent limit. The SDK retries `429` for you and honors `Retry-After`.

### Keep keys safe

- Keep keys out of client-side code, browsers, and mobile apps.
- Store them in environment variables or a secrets manager, never in source control.
- Give each key the narrowest set of scopes it needs.
- Set an expiration on keys that are only meant to be temporary.
- Revoke any key you no longer use, or that may have leaked.
