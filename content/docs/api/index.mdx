The developer API lets your own systems use the workflows you've built in Lodol: list them, start runs with the inputs they need, follow each run to its result, answer the approval requests runs wait on, and stop, retry or delete a run. Workflows are usually built in Lodol or by your [AI tool](/docs/build-with-ai), and the API can create and change them too, in the [workflow format](/docs/api/workflow-format).

## Base URL

Every endpoint is under one base URL:

```txt
https://api-prod.lodol.com/api/v1
```

## Endpoints

| Endpoint | What it does | Scope |
| --- | --- | --- |
| [`GET /workflows`](/docs/api/workflows#list-workflows) | List the workspace's workflows | `workflows:read` |
| [`GET /workflows/:id`](/docs/api/workflows#get-a-workflow) | Get one workflow, with its steps | `workflows:read` |
| [`POST /workflows`](/docs/api/workflows#create-a-workflow) | Create a workflow | `workflows:write` |
| [`PUT /workflows/:id`](/docs/api/workflows#replace-a-workflow) | Replace a workflow's steps, name or description | `workflows:write` |
| [`PATCH /workflows/:id`](/docs/api/workflows#edit-a-workflow) | Change part of a workflow's steps | `workflows:write` |
| [`POST /workflows/validate`](/docs/api/workflows#validate-a-workflow) | Check a workflow without saving it | `workflows:write` |
| [`DELETE /workflows/:id`](/docs/api/workflows#delete-a-workflow) | Delete a workflow for good | `workflows:delete` |
| [`POST /workflows/:id/run-async`](/docs/api/runs#run-a-workflow) | Start a run | `workflows:execute` |
| [`GET /executions`](/docs/api/runs#list-runs) | List runs | `executions:read` |
| [`GET /executions/:id`](/docs/api/runs#get-a-run) | Get a run's status and results | `executions:read` |
| [`POST /executions/:id/stop`](/docs/api/runs#stop-a-run) | Stop a run | `workflows:execute` |
| [`POST /executions/:id/retry`](/docs/api/runs#retry-a-run) | Retry a failed run | `workflows:execute` |
| [`DELETE /executions/:id`](/docs/api/runs#delete-a-run) | Delete a finished run for good | `executions:delete` |
| [`GET /approvals`](/docs/api/approvals#list-approval-requests) | List approval requests | `executions:read` |
| [`GET /approvals/:id`](/docs/api/approvals#get-an-approval-request) | Get one approval request | `executions:read` |
| [`POST /approvals/:id/decision`](/docs/api/approvals#answer-an-approval-request) | Approve, reject or reply to one | `workflows:execute` |

The API calls a run an **execution**: run IDs are `execution_id`, and their endpoints are under `/executions`.

## Requests and responses

- **Authentication.** Send your API key as a bearer token: `Authorization: Bearer sk_live_…`. See [Authentication](/docs/api/authentication).
- **JSON.** Request bodies are JSON, sent with `Content-Type: application/json`. Every response is JSON.
- **Timestamps** are ISO 8601 with an offset, such as `2026-03-17T08:00:00+00:00`.
- **Errors** have a JSON body with an `error` message and a standard HTTP status. See [Errors and retries](/docs/api/errors).
- **Retries.** Send an `Idempotency-Key` with each run you start and each workflow you save, so retrying a request never does the work twice. See [Idempotency](/docs/api/errors#idempotency).
- **Limits.** Requests are rate-limited per workspace, by plan. See [Limits](/docs/api/limits).

## Paging through lists

[List runs](/docs/api/runs#list-runs) returns results a page at a time. Pass `limit` (1 to 100, default 20) for the page size, and `after` with the last ID of the page you have to get the next one. [List approval requests](/docs/api/approvals#list-approval-requests) pages the same way, but its cursor is `before`, set to the `next_before` the page came with.

```bash
# First page
curl "https://api-prod.lodol.com/api/v1/executions?limit=20" \
  -H "Authorization: Bearer $LODOL_API_KEY"

# Next page: after = the last execution_id of the previous page
curl "https://api-prod.lodol.com/api/v1/executions?limit=20&after=683b2c3d4e5f6a7b8c9d0e1f" \
  -H "Authorization: Bearer $LODOL_API_KEY"
```
